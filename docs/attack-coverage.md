# MITRE ATT&CK coverage

Each WatchLattice alert that is evidence of an adversary technique carries
that technique's [MITRE ATT&CK](https://attack.mitre.org/) ID. The ID is
shown in the dashboard's alert details, written to the Windows Event Log
(data string 10, and a line in the readable text; see
[the Event Log contract](event-log.md#what-an-entry-contains)) and included in
alert exports. IDs follow **Enterprise ATT&CK v20.1**.

## What a mapping means, and what it doesn't

- **A mapping says what an alert is evidence of. It is not a claim that
  WatchLattice blocks the technique, or catches every use of it.** Every
  module reports a change *after* it happened, at its next check (for
  example every 5 minutes for autostart entries). Nothing is blocked or
  undone.
- **An attacker with administrator rights can stop the hub** (or hide from
  it) before making the change. WatchLattice is a second pair of eyes next to
  Microsoft Defender, not a replacement for it.
- **Direct** means the alert reports the technique's own artifact: a new Run
  key value *is* T1547.001. **Related** means the alert reports a change the
  technique is one common cause of, and ordinary software causes it too: a
  hosts file edit can be adversary-in-the-middle, or an ad blocker.
- Health, baseline, removal and recovery alerts (`STATUS_UNAVAILABLE`,
  `BASELINE_CREATED`, `ENTRY_REMOVED`, `*_CLEARED` and the like) have no
  technique.
- ATT&CK v18 replaced the Impair Defenses techniques: **T1562.001** is now
  **T1685** (Disable or Modify Tools) and **T1562.004** is now **T1686.003**
  (Windows Host Firewall). If a SIEM rule still keys on the old IDs, add the
  new ones.

## Checked on a real machine

The [detection checks](../demos/detection-checks.md) make one harmless,
self-reverting change for most rows below (a Run key value pointing at a
program that does not exist, a disabled scheduled task, a WMI filter with no
consumer, a firewall rule for a missing program, and so on), run the real
module code once and record whether it raised the expected alert. CI runs
them on a fresh Windows runner for every pull request that touches the
modules, and [RESULTS.md](../demos/RESULTS.md#detection-checks) has the
latest run.

Rows the checks do not exercise, because the change would weaken the PC even
briefly (turning off real-time protection or a firewall profile, lowering
the cloud block level, turning off tamper protection), are covered by unit
tests against recorded readouts and by the [Windows hand checks](windows-checks.md).

## Known gaps

Techniques common on Windows that WatchLattice does **not** watch today, so
that nobody mistakes the table above for full coverage:

| Technique | Why it isn't covered |
|---|---|
| T1003 OS Credential Dumping (LSASS) | Needs process-access telemetry or a kernel driver; WatchLattice is user mode only. Defender's ASR rule *Block credential stealing from LSASS* covers it. |
| T1055 Process Injection | Same: no user-mode polling can see it reliably. |
| T1490 Inhibit System Recovery (shadow copy deletion) | Not watched yet. A candidate for a future check. |
| T1685.005 Clear Windows Event Logs | Not watched yet. A candidate for a future check. |
| T1068 Exploitation for Privilege Escalation and T1687 Exploitation for Defense Impairment (vulnerable drivers) | Needs driver-load telemetry; out of scope for a user-mode tool. Microsoft's vulnerable driver blocklist covers part of it. |
| T1021 Remote Services, lateral movement | Network and logon telemetry belong to Defender for Endpoint or a SIEM. |
| T1566 Phishing, initial access | Mail and browser protection belong to Defender SmartScreen and the mail client. |

Suggestions and corrections to the mapping are welcome: open an issue, or a
pull request against `src/WatchLattice.Common/Alerts/AttackMapping.cs`.
